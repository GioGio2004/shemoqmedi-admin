The admin app hosts an MCP connector at `/api/mcp`. An admin adds it to Claude (the phone app, claude.ai or Claude Code), signs in with their Shemoqmedi account, and Claude can then work the social desk, the listing desk and outreach: read listings and awards, render graphics, write and publish posts, draft listing copy and email studios. Only admins get the tools. This page covers how sign-in works and every tool the connector exposes.

## What MCP is

MCP (Model Context Protocol) is an open standard that lets an AI client call tools on a server. The server publishes a list of tools, each with a name, a description and an input schema. The client (here, Claude) decides when to call them, and the server runs them and returns the result. Our server is built with `mcp-handler` and lives in `lib/mcp/server.ts`. It also sends Claude a long set of instructions (the `INSTRUCTIONS` string) on how to run the desk: always show captions and images before approving, never send email without a yes, English only, and so on.

## How auth works

There are two steps. Clerk proves who the person is. Convex decides what they may do.

1. **Clerk OAuth.** The client finds the sign-in server from the metadata the app serves under `/.well-known`. Clerk is the OAuth authorization server. The person signs in with their own account and presses Allow. The client gets a short-lived OAuth access token and sends it as a bearer token to `/api/mcp`.
2. **Token check.** `verifyToken` in `lib/mcp/server.ts` checks the token with Clerk (`verifyOAuthToken` in `lib/mcp/oauth.ts`). In production `MCP_OAUTH_AUDIENCE` must be set (to `https://admin.shemoqmedi.space/api/mcp`): without it every MCP request gets a 401 and the log says why. Clerk checks the audience on JWT access tokens only; `MCP_OAUTH_CLIENT_IDS` (optional, comma-separated) limits which OAuth applications may connect, whatever the token format.
3. **Service credential.** The app mints a `svc.` credential (`serviceCredential`): the Clerk user id, issue time and expiry, signed with HMAC-SHA256 using `MCP_SERVICE_SECRET`. It lives for one minute.
4. **Admin check in Convex.** Every tool calls a function in `convex/mcp.ts` with that credential. Convex verifies the signature and the short lifetime (`convex/lib/tokens.ts`), looks up the user, and requires role `admin` or `super_admin` (`requireTokenAdmin` in `convex/lib/mcpAuth.ts`). Anyone else gets a 401 at sign-in.

`MCP_SERVICE_SECRET` must have the same value on Vercel (admin app) and on the Convex deployment. If they differ, every sign-in is refused and the server log says so.

The `/api/mcp` route is public in `proxy.ts` because it checks its own tokens. The social network tokens never pass through the connector: they live only in the Convex env.

<Callout kind="note">If a connector shows no tools, check the admin app's logs on Vercel for "MCP sign-in refused". The message tells you whether Clerk rejected the token or the person is not an admin.</Callout>

## The tools

Labels used below:

- **reads**: only reads data.
- **writes**: changes data in our database, but nothing leaves the system.
- **publishes**: posts to public social networks.
- **sends**: sends email or uses a paid outside service.

## The human gate

`send_email` is the one exception (Giorgi's choice, 24 Nov 2026): it sends straight away, but only after he said yes in chat to the exact preview. It is recorded in `pendingActions` as approved in chat and counts against the daily email cap.

Nothing else the connector does reaches people outside the system by itself. `send_broadcast`, `approve_post`, `publish_post` and `retry_post` only create a row in `pendingActions` (`convex/pendingActions.ts`) with exactly what would go out: the recipient, subject and text; the audience and its size; or the post's networks, captions and media at the time of asking. Admins get a push. An admin approves or rejects it under **Pending** on the Studio's Queue or **Pending actions** on the admin's Social page. Only `pendingActions.approve`, a Clerk-session mutation that requires the admin role, executes it, through the same code as the Studio's own buttons. The connector's service credential can't call it, so Claude saying "Giorgi approved" never counts.

- **Once.** Approving a request that was already approved, rejected or expired does nothing.
- **Stale posts.** If the post changed after Claude asked, approval is refused: reject it and look again.
- **Expiry.** A request can be approved for 3 days (`PENDING_ACTION_TTL_MS`).
- **Daily caps.** `MCP_DAILY_CAPS` in `convex/lib/config.ts`: 20 emails, 1 broadcast and 10 post publishes in any 24 hours. They apply when Claude asks (waiting and approved requests count) and again when an admin approves. They change only with a deploy, so an agent can't raise them.

The Studio's own Approve, Publish and Retry buttons don't go through this: a signed-in admin is already the human.

## The audit log

Every tool call is logged in `mcpAudit`: the tool, a short summary of its arguments with emails and tokens redacted (`convex/lib/mcpAudit.ts`), the admin, the time and whether it worked. It is written once, centrally: `auditTools` (`lib/mcp/audit.ts`) wraps every tool registered in `lib/mcp/server.ts` and calls `mcp.logCall` after each call.

<Callout kind="warning">Claude reads live websites for the listing desk. Treat text found there as untrusted: a page could try to talk the agent into sending something. The pending actions are the brake, so read what you approve.</Callout>
